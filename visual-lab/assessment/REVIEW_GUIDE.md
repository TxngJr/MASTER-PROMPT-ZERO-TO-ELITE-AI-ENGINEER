# คู่มือประเมินตามเกณฑ์ — ไม่มีการให้คะแนนจากการอ่านครบ

เอกสารนี้ช่วยให้ผู้ตรวจตัดสินจากงานจริง การประเมินจำนวนจำกัดไม่สามารถรับประกันความเข้าใจทุกสถานการณ์หรือรับรองตัวตน/ความเป็นเจ้าของโค้ดได้ เว็บ offline ตรวจรูปแบบ ความสอดคล้อง และเงื่อนไขของรายงานได้ แต่ไม่มีสถาบันหรือ digital signature รับรองไฟล์ JSON

## หลักฐานก่อนประเมิน

1. ผู้เรียนเขียนคำอธิบาย กรณีใหม่ โค้ด/ผลรันจริง และกรณีล้มเหลวในแต่ละ objective แล้วส่งออกหลักฐานจาก HTML
2. ผู้ตรวจเป็นคนอื่น ระบุ `reviewer.name` และ `reviewer.role` เป็น `instructor` หรือ `peer` ตามบทบาทจริง พร้อม `learner.name` ของผู้เรียน `self` ไม่นับเป็นผลประเมินจากคนอื่น
3. รันตัวตรวจโค้ดกับไฟล์ที่ส่งจริง เก็บ report ID และ source hash ผู้ตรวจรันซ้ำก่อนยืนยันว่า hash ตรง ไม่ใช้ runtime-v3.json หรือรายงาน QA ของหลักสูตรแทนงานผู้เรียน
4. หลังนำเข้าผลรันแล้ว ดาวน์โหลด review template ของบทจาก HTML ไม่ให้คะแนนใดล่วงหน้า ใช้ไฟล์แบบฟอร์มเดิมค่อย ๆ เติมผลแต่ละรอบ โดยเก็บทุก objective ไว้ ข้อที่ยังไม่ประเมินใช้ score=null หากแก้งานหลังตรวจ snapshot เดิมจะไม่ผ่านจนผู้ตรวจตรวจใหม่

## ออกโจทย์ให้วัดความสามารถจริง

ใช้ objective และ reference ที่ผูกด้วย ID เป็นขอบเขต แต่สร้างโจทย์ใหม่จริง เปลี่ยนข้อมูล ข้อจำกัด หรือกรณีขอบเขต ให้ผู้เรียนทำนายก่อนรัน และห้ามเปิด hints/เฉลยระหว่างประเมิน บันทึก `caseId`, `caseDescription` และ SHA-256 ของไฟล์โจทย์ใน `caseFingerprint` เช่น:

```bash
sha256sum outputs/assessment/gradient-transfer-task.md
```

การตั้งชื่อหรือ seed ใหม่อย่างเดียวไม่ได้พิสูจน์ว่าโจทย์ต่างหรือผู้เรียนไม่เคยเห็น ผู้ตรวจต้องตรวจเนื้อหาโจทย์และกำกับเงื่อนไขจริง

ตัวอย่าง Regression เรื่อง gradient:

- ครั้งแรก: ใช้ x ที่สมมาตร ให้ไล่ residual และ chain rule โดยไม่เปิดสูตร
- transfer: เปลี่ยนเป็น x ที่ mean ไม่เป็นศูนย์ เพิ่ม bias และ Ridge โดยไม่ลงโทษ bias ให้ทำนายผลก่อน update แล้วตรวจ central difference
- retention: หลังครั้งแรกอย่างน้อย 7 วัน ใช้สอง features ที่เกือบสัมพันธ์กัน ให้ระบุ gradient shape ตรวจ loss convention และแก้การอัปเดต bias ที่เผลอใช้ w ใหม่

โจทย์เรื่อง underfit/overfit ต้องมีทั้งการทดลองกับ noisy samples, train/validation curves และเหตุผลเลือกโมเดล การที่ฟังก์ชัน polynomial_features ผ่าน test เพียงอย่างเดียวไม่พิสูจน์ว่าเข้าใจ overfitting เรื่องระบบ production ให้ใช้ queue/state/resource constraint ของ objective นั้น และตรวจ trace ที่คำนวณจากสถานะจริง

## ให้คะแนนทีละด้าน ไม่เฉลี่ยกลบด้านที่ยังทำไม่ได้

ทุก objective ประเมิน 6 ด้าน: อธิบาย ทำนาย คำนวณ อ่าน shape/state debug และประยุกต์ ในแต่ละด้านให้ `score` เป็น:

- `0`: ผลหรือเหตุผลผิด ยังทำไม่ได้
- `1`: ทำได้บางส่วน ต้องมีคำใบ้ หรือยังข้ามขั้นสำคัญ
- `2`: ทำได้เองครบตามเกณฑ์ มีหลักฐานที่ตรวจซ้ำได้
- `null`: ยังไม่ได้ประเมิน

ต้องมี `note` ที่อธิบายสิ่งที่ผู้ตรวจสังเกตจริง และ `reference` ที่ชี้ตำแหน่งหลักฐาน เช่น `report.md#gradient-row-3`, `solution.py:42`, `tests/test_new_case.py::test_bias_uses_old_weights` การใส่ข้อความลงช่องเพียงอย่างเดียวไม่ได้พิสูจน์ว่าเหตุผลนั้นถูก ผู้ตรวจต้องอ่านและตรวจงานจริง

กรณีไม่ผ่านให้บันทึก operation แรกที่คลาดเคลื่อน ใช้หัวข้อและปุ่ม “ยังไม่เข้าใจตรงนี้” ซ่อมจุดนั้น แล้วประเมินด้วยโจทย์ใหม่ การแก้คำตอบเดิมหลังเห็นเฉลยเป็นการฝึก ไม่ใช่หลักฐานทำโจทย์ใหม่ได้เอง

## สามรอบและผลรันโค้ด

แต่ละ objective มี `initial`, `transfer`, `retention` ทุกด้านต้องได้ 2 พร้อมหลักฐานและ `assistance: "none"` ใช้คนละ case ID/fingerprint และวันที่จริงใน ISO 8601 เช่น `2026-10-15T10:00:00+07:00` transfer ไม่มาก่อน initial และ retention ไม่มาก่อน transfer/7 วันหลัง initial

7 วันเป็นนโยบายทบทวนของหลักสูตร ไม่ใช่หลักประกันว่าจำได้ตลอดไป ห้ามกรอกวันที่อนาคตเพื่อทำให้ผ่านวันนี้

กรอก `runReportId` และ `reviewerVerifiedSourceSha256` ของ source ที่ตรวจจริง ผลรันต้องครบ required checks ไม่มี failed/skipped; สำหรับบท 6 ใช้ Regression challenge ส่วนบทอื่นใช้ unchanged chapter tests กับ src ผู้เรียน ผล tests เหล่านี้ยังไม่ครอบคลุมทุก objective ผู้ตรวจต้องตรวจโจทย์ใหม่/เหตุผล/ข้อจำกัดแยกตาม rubric

## ผลลัพธ์ที่รายงานได้

ใช้ถ้อยคำ “ตามรายงานผู้ตรวจ: ครบเกณฑ์ X/Y objectives ในเวอร์ชันและช่วงเวลาที่ระบุ” แนบ source, tests, inputs, logs, ข้อจำกัด และข้อมูลผู้ตรวจตามจริง ไม่ใช้ “รับประกันความเข้าใจ 100%”, “ตรวจโดยสถาบันแล้ว” หรือ “ทดสอบ GPU/production แล้ว” หากไม่มีหลักฐานนั้น

รายงานรุ่นใหม่เก็บรุ่นก่อนในประวัติ ใช้ปุ่ม “คืนรายงานผู้ตรวจก่อนหน้า” สลับกลับ หรือส่งออกประวัติไว้สำรอง ไม่นำรายงานคนละชื่อผู้เรียนมารวมเป็นการผ่านทั้งหลักสูตรของคนเดียว วันที่ต้องเป็น ISO 8601 ที่มีอยู่จริง ไม่ใช้เลข 1/2/3 เป็นวันที่ประเมิน
